# 公开资料不足时的人工处置与流程结束

本变更基于 PR #8 合并后的 main `4043669`。公开资料核查可以完成，但并不意味着所有事实都已证实。未知不补零，不将不确定项确认成事实，也不以降低覆盖率的方式伪造最终分。

## 使用方式

业务工作台的每条当前指标和检查建议新增“人工核查处置”。用户可选择：

- `confirm`：确认已披露事实或既有非未知判断，需理由及本任务证据。不能确认未知、冲突或解析失败记录。
- `insufficient_evidence`：已人工核查，公开资料不足。理由、检索范围、缺失材料及使用限制均必填。
- `reopen`：重新打开核查，保留旧处置历史。

这是既有值的确认和证据不足处置，不含数值修正接口；不会恢复旧E02被清空的值。E02技术校验失败、parse_error、conflict不能作为公开资料不足结案，应先修复或走正式纠错流程。

实际三项可按当前记录分别登记，不预置、不自动关闭：

| 未决事项 | 保留事实 | 使用限制与所缺材料 |
|---|---|---|
| 强度分子分母范围 | 保留报告披露强度和万元营收单位；范围仍待确认 | 不自行造分母，不作确定效率解释；需排除范围、对应营收和分母说明 |
| 2023范围2因子 | 保留排放量，实际因子未知 | 反推比值不是正式因子，不据此确定归因或同比；需企业因子表、活动数据、GWP及边界说明 |
| 2023范围3 | 保留原文“/”、missing_marker和空数值 | 不填0，不认定未盘查、不计算同比；需类别、边界及盘查资料 |

这不是单独待办事项管理器：每项处置绑定具体record_id或check_id。若同一问题影响多个年度或指标，需要分别关联；文字中可注明PEND编号。其他确认、复核及验收步骤仍需逐项完成。

## 用户接口

- `POST /tasks/{task_id}/review-dispositions`
- `GET /tasks/{task_id}/review-dispositions`：返回current与history。

仅接受用户会话，Agent令牌拒绝；前端同源cookie提交。仍沿用本地单用户原型认证，不声称已完成生产多用户归属认证。

POST字段：expected_revision（整数）、target_type（metric/check）、target_id、decision、reason；证据不足时另要求search_scope、missing_material、limitations非空。拒绝额外字段，不能提交新数值、操作者或人工确认状态。target_id必须是当前任务的当前有效记录，引用必须仍在该任务范围。操作中的任务返回RUN_BUSY；旧版本返回REVISION_CONFLICT。

保存时用同一SQLite事务记录操作者、UTC时间、原目标快照、报告版本/哈希、引用页码、处置内容与新revision。不改变原值或缺失标记。证据不足的指标仍为unreviewed，检查项按unknown处理；UI分别展示“已人工核查，证据不足”与“事实未证实”。

指标处置使依赖检查失效，需要重建并复核；比较及旧导出过期，评分缓存清除。依赖于仍有效的指标不确定性，相关检查即使被后续模型写成met，评分仍按unknown处理，不能确认以绕过限制。现有METRIC_TO_CHECKS是保守依赖表，可能牵涉多项检查。

每项处置保存目标指纹。目标值、证据、状态、来源或复核状态改变后，旧处置不再满足完成门槛；新record_id、过期记录亦不会继承旧处置。无关任务revision增加不会单独使全部处置失效。reopen保留审计但重新要求处理。

## 运行与评分门槛

正常结束仍要求：SDK正常回合、当前版本get_task_results成功审计、六指标选定年度覆盖、20个不同规则检查均有效、每项已确认或有当前有效人工处置，以及当前版本导出成功审计。缺少任何一项仍暂停或失败，不能凭模型答复结案。

当全部处理门槛满足且仍有insufficient_evidence处置时，运行状态为 `completed_with_limitations`，页面显示“核查流程已完成，存在使用限制”。它不是completed的数据全确认结论，更不等于Task 7项目验收通过。旧run不自动改状态；正式复核后需再按授权范围继续运行。主模型与提取费用额度、真实持久会话恢复、Task 8等验收项仍独立存在。

评分规则权重及公式不变。unknown不获得分值，不自动N/A；不足全覆盖时final_score保持空，参考分与区间按既有公式计算。比较仍受原review_state、边界、方法和单位门槛约束。

## 导出与兼容性

- JSON新增review_dispositions，包含当前有效处置及证据、版本和人工信息。
- Markdown新增人工处置与使用限制段。
- CSV在原指标列后追加review_decision、review_reason、search_scope、missing_material、use_limitations、review_target_type、review_target_id。检查项处置另占类型为check的行，指标列留空，不能当成指标数据行。所有新增单元格沿用公式注入防护。

Agent领域工具和MetricRecord/DisclosureCheck schema未新增人工权限或伪造的事实状态。宿主通过可信任务数据向模型告知已有人工处置，最终仍重读后端状态判定。

## 验收

离线覆盖权限拒绝、必填字段、版本冲突、外任务目标、数值覆盖拒绝、持久化及重启、事务回滚、状态重开、证据变化失效、技术错误不可冒充缺证、缺失标记保留、受限评分与导出，以及正常SDK回合下带限制结束且缺导出仍不放行。未对真实业务数据库批量确认，未调用真实模型。

## 批量导入的后续验收门槛（与本变更分开）

队长补充的四步作为后续导入验收，当前尚未实现或执行批量导入，也未读取、校验《导入映射.xlsx》。资料中所述11条可用、4条pending及9个partial是待逐条映射核对的输入规模，不等同于历史任务的12条指标记录。

1. **3个PEND与4条观察记录。** 取得企业补证后，应由人工核实证据、口径及所有受影响记录，再决定resolved与usable；不能因收到文件就自动usable=true。没有材料时，最终答案候选区只接收明确usable=true且满足证据/规则要求的记录；4条pending不作为已确认答案。若系统另行保留它们，应进入待确认/审计区并带caveat。因此“导入后抽查4条pending”是检查隔离区，而非把它们混进最终答案。
2. **正式20项。** 产品已有`backend/src/esg_app/rules/disclosure-v0.1.json`和`rules_registry.py`的20个正式检查ID。资料建议项须按ID、规则版本和锚点映射，不能直接替换产品规则。partial是既有评分规则的部分满足状态（按规则计0.5），与“存在待确认事实”或“pass with caveat”不是同一维度；9项需逐项核对锚点及证据。只有确实未满足产品验收要求的项才阻塞，不强行改met。
3. **宁德时代。** 是否进入系统仍由队长决定，未确认前不自动导入；仅归档时不要求其完成系统验收。若正式启用，须补齐六指标及20项独立参考材料，并隔离盲测输入与答案。
4. **dry-run。** 先取得实际导入映射及其契约，在任务副本或staging校验obs_id/evidence_id/report_id、报告哈希、年度、单位、引用页、重复/外任务ID、规则映射、可用性与pending标记。dry-run不写生产数据，也不产生模型调用。`usable_for_scoring=false`、`pending`不得被忽略或映射为confirmed；未知标记或冲突字段应拒绝/隔离，不能按真值字符串处理。usable=true也不直接等于人工已确认。

建议dry-run报告分别列出：最终答案候选数、隔离pending数、被拒绝数及原因、正式检查映射和partial处置。抽查4条pending时，核对原始标记、caveat、所缺材料、评分不可用性和人工审计，并验证没有进入最终答案。该导入器及字段映射属于后续独立改动，本PR不能充当其测试通过证明。
